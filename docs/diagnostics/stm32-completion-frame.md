# STM32 完成帧接收排查（2026-09-20）

范围：外部 STM32F103 客户端的 `DFCom_Example` 和 `DFCom_PatchOnly`。本次检查没有连接真板，也没有修改底盘固件或客户端接收实现。以下缺陷在本次主线合并前已存在。

## 离线复现结果

复用 `tests/host/test_move_slots.c` 的串口桩、状态重置与合法回包构造函数，直接编译两个目录现有的 `DFCom_Rx.c` / `DFCom_Tx.c`，向解析器送入 `A=0x6F, B=CMD_LINEAR, LEN=2, Process=0xFF, Notice=0` 的 11 字节合法完成帧。

| 输入方式 | 两份 STM32 客户端的结果 |
|---|---|
| 完整 11 字节一次输入 | 进度正确更新为 255 |
| 在第 1 至第 10 字节后分别拆成两次输入 | 10/10 种拆分均未识别完成 |
| 单次 231 字节，含 20 条中间进度帧及第 21 条完成帧 | 只处理前 20 条，进度停在 128，未更新为 255 |

复现步骤：每种输入前重置并启动运动会话、注册一条直线任务；构造带正确地址、帧尾和校验和的帧；调用 `DFCom_RxParse` 后读取 `GetMoveProgress(CMD_LINEAR)`。拆分输入时不改变或丢弃原始字节，仅改变两次调用的边界。

## 已确认的源码原因

1. `DFCom_RxParse` 的 `pos` 是每次调用重新初始化的局部变量；遇到不完整帧直接 `break`，没有残留缓冲区。注释“等下次中断”并没有相应拼接实现。USART1 IDLE 中断解析后还会清空接收区、重装 DMA 计数。因此只要一个有效帧跨越两次接收批次，就无法靠下一批补齐。
2. 解析循环被 `MAX_ITER=20` 限制，剩余数据不保存。231 字节仍在 256 字节接收缓冲区以内，21 条合法短帧就能触发遗漏；噪声中的假帧头也可能消耗迭代次数。该输入是边界测试，不代表正常配置下一定会出现这种批次。
3. A/B 任务槽优先吞掉旧任务同命令码的回传。若旧任务的唯一终止帧已丢失，后续同类任务的完成帧可能被当作旧槽终止帧消耗。现有 `test_lost_terminal_never_causes_false_early_done` 已覆盖这种保守超时策略；它不能证明当前任务没有完成。

## 需要真板测量的风险

USART1 使用 Normal DMA，IDLE 中断中先停 DMA，再解析并清空缓冲，最后重启。该窗口内到达的字节，以及连续输入超过 256 字节的情况存在接收风险；本次没有采样 ORE、DMA 计数和中断时序，不能给出现场丢帧概率或断言这是当前故障原因。

建议真板诊断分别统计：接收字节/批次数、DMA 满缓冲、USART ORE、有效终止帧、校验失败、旧槽丢弃终止帧、等待超时。计数低频汇总，避免在接收中断中大量打印。

## 结果语义与后续修复方向

`Process=0xFF` 表示任务终止，只有 `Notice=0` 才是正常完成；被打断、拒绝等情况不能显示为成功到位。完成帧丢失后，有界等待会超时；`timeout=0` 可能一直等待。当前等待超时本身不发停车指令。

下一步应先用“正确识别拆分完成帧”和“正确处理缓冲区内所有合法帧”的失败回归测试驱动小范围接收器修复，同步两份 STM32 客户端；随后真板验证 DMA 接收窗口。不要通过盲目接受下一条 `0xFF` 来绕过旧槽保护。若需从协议层消除任务归属歧义，需要另行设计 task id 或可靠终态确认机制。
