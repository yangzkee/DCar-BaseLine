# DFLink 队列 v6：当前客户端通信契约

本文对应STM32的 `DFQueue_*` 和ROS 2的 `motion_protocol: queue` / `/trajectory`。
DFLink V3是外层协议族名称，**队列v6是运动能力版本**，两者不是同一个版本号。
底盘固件不在本仓库发布；队列客户端开始前必须查询能力和下一任务ID。

## 重点一：连续队列怎样发送、怎样接收

连续队列允许在前一段尚未完成时提交后续段，由车端排队执行。每段有独立任务ID；发送者收到入队确认即可继续提交，不必先等该段DONE。
它与“完成整圈后再循环下一圈”是两层机制，也不等于保证段间不停轮、恒速通过或曲线平滑拼接。

当前STM32操场例程先提交四段，再依次等待四个ID完成；本地最多跟踪8条，握手时按设备16槽空闲判断队列为空。

| 次序 | 客户端发送 | 车端回包 / 客户端判定 |
|---|---|---|
| 1 | A=02/B=85，payload=`00` | A=6F/B=85，notice=21，最后U16为能力值，要求>=6 |
| 2 | A=02/B=85，payload=`07` | notice=28，最后U16为下一任务ID，要求非零且process=16 |
| 3 | 运动帧，末尾附任务ID | A=6F/B=85，payload=`process, notice, ID低字节, ID高字节` |
| 4 | 收到该ID的入队确认后继续发下一段 | process=0/notice=10仅表示入队，不表示完成 |
| 5 | 持续接收各ID状态 | process=255，notice=00或27才按成功完成处理 |

本表A/B与notice按十六进制表示，process和能力数值按十进制表示。
入队确认丢失时重发原ID、原帧；入队后的完成回包丢失时，用 `A=02/B=85, payload=05+ID:U16LE` 查询该任务结果。
notice=11表示队列满，保留原ID重试；notice=25表示仍在微调，26表示超差失败，27表示微调时限到达但仍在容差内。终态还须检查process，不能只看notice。

## 重点二：直线运动怎样发送、怎样接收

当前队列直线统一使用 **A=0x02、B=0x64**。接口为：

```c
DFQueue_Linear(x_m, y_m, speed_mps, yaw_rad, grade);
```

`grade`是加速度档位：16极低、17低、18中、19高、20极高；当前例程使用18。
它不是旧无ID接口的profile=0/1/2。下表偏移从payload首字节开始。

| payload偏移 | 仅平移，LEN=15 | 平移同时转向，LEN=19 |
|---|---|---|
| 0..3 | x:S32 | x:S32 |
| 4..7 | y:S32 | y:S32 |
| 8..11 | speed:S32 | speed:S32 |
| 12..15 | 偏移12为grade，13..14为ID | yaw:S32 |
| 16..18 | 无 | 偏移16为grade，17..18为ID |

所有多字节字段均小端；x/y单位m、speed单位m/s、yaw单位rad，四项均乘10000编码成S32。
speed要求正数，前后左右由x/y正负确定；坐标约定为+X前、+Y左、正yaw逆时针，位移/转角相对该段起点。
客户端在yaw=0时发15字节payload，yaw非零时发19字节payload。扩展帧表示该段平移同时转向，不是先平移结束再原地转向。

```c
// 后退0.60m，不附加转向：LEN=15
id = DFQueue_Linear(-0.60f, 0.0f, 0.15f, 0.0f, 18);

// 后退0.60m，同时转+360度：LEN=19
id = DFQueue_Linear(-0.60f, 0.0f, 0.15f, 6.283185307f, 18);
```

后一例的yaw编码约为62831，表示相对转角+2π；不能把它归一化成0，否则会丢掉整圈转向要求。
两种直线的接收格式都使用队列统一回包 `A=0x6F/B=0x85, process:U8 + notice:U8 + ID:U16LE`，根据ID对应任务。
Odom用于观察姿态、速度和位置，不代替该ID的完成回包。

ROS队列输入当前仍沿用字段名 `profile`，编码器把其16..20值装入上述grade字节；该名字是客户端接口现状，不是当前队列多出一种运动模式。下文无ID接口仅供核对独立功能，不用于解释这里的队列直线。

## 1. 公共帧和数值

```text
DF target source A B LEN payload FD checksum:u16LE
```

默认客户端source=0x97、车端target=0x01。回包交换两个地址。
LEN只计payload，整帧LEN+9字节；checksum为从DF到FD（均包含）的16位累加和，小端序。
接收器验证地址、帧尾、校验和和所需长度，再分发内容；串口分包/粘包不是帧边界。

运动中的S32为有符号32位小端定点数：物理值乘10000、向零截断。
不是IEEE754浮点。单位为m、rad、m/s、rad/s；+X前、+Y左、+Z上，正yaw逆时针。
位移与转角相对每段起点，不是全局绝对坐标。速度和能力受底盘约束。

## 2. 队列运动帧

所有运动发送A=0x02，ID是1..65535的U16小端，0不是有效任务ID。

| B | payload按线上顺序 | LEN |
|---|---|---:|
| 0x64直线 | x:S32, y:S32, speed:S32, grade:U8, ID:U16 | 15 |
| 0x64平移并转向 | x:S32, y:S32, speed:S32, yaw:S32, grade:U8, ID:U16 | 19 |
| 0x66圆弧 | radius:S32, yaw:S32, signed_speed:S32, grade:U8, ID:U16 | 15 |
| 0x63原地旋转 | yaw:S32, omega:S32, ID:U16 | 10 |

直线speed>0，后退使用负x；yaw=0使用15字节直线，yaw非零使用19字节扩展直线。
ROS `command=101/0x65`只是输入别名，队列线上仍编码为扩展0x64。
圆弧radius>0、speed非零，负速度倒行。原地旋转omega>0，方向由yaw符号决定。

直线/圆弧grade为16/17/18/19/20，对应极低/低/中/高/极高。原地旋转线上没有grade字段；ROS队列输入仍要求profile填16..20以通过统一校验。
这些是档位编号，不是以m/s²为单位的直接加速度参数；具体加速度和限速由车端固件决定。

示例：前进0.1m、速度0.06m/s、中档18、ID7：

```text
DF 01 97 02 64 0F E8 03 00 00 00 00 00 00 58 02 00 00 12 07 00 FD 47 04
```

## 3. 队列管理与握手

发送A=0x02、B=0x85：

| payload | 请求 | 对应回包含义 |
|---|---|---|
| `[0]` | 查询能力 | notice=0x21，ID字段为能力版本，须>=6；客户端不检查此回包的process |
| `[7]` | 查询下一ID | notice=0x28，ID为下一编号；当前客户端要求process=16（设备16槽全部空闲） |
| `[5, ID:u16LE]` | 查询指定任务结果 | 回该ID的进度/终态 |
| `[4]` | 取消队列 | 客户端同时尝试发送零速度 |

`Begin`依次完成能力与下一ID查询；设备队列非空或查询失败则不开始运动，不静默降级。
一个设备只允许一个队列发送者，不能由STM32和ROS同时抢占编号。
任务ID按1..65535循环，断线后不自动重放，下一批重新查询编号。
协议没有会话号；有限结果历史不能消除设备重启或完整编号循环后无限迟到旧包的歧义。

## 4. 入队、进度与完成

回包A=0x6F、B=0x85、LEN=4：

```text
process:U8, notice:U8, ID:U16LE
```

| process | notice | 含义 | 是否成功终态 |
|---|---|---|---|
| 0 | 0x10 | 入队确认 | 否 |
| 1..254 | 0 | 执行进度 | 否 |
| 254 | 0x25 | 到位，仍在末端微调 | 否 |
| 255 | 0 | 正常完成 | 是 |
| 255 | 0x27 | 微调时限到达但仍在车端容差内 | 是 |
| 255 | 0x26 | 微调超差 | 否，失败 |
| 任意 | 0x11 | 队列满，原ID重试 | 否 |

其他notice按失败处理。ID0是整体通知，不作为某条任务结果。
重复终止只消费一次；迟到ACK/进度不能重新打开已完成任务。
未收到入队确认时，使用原ID、原字节重试；已确认入队后终止丢失则查询该ID，不重复创建运动。

STM32最多8个本地跟踪槽，成功 `Wait` 消费结果后释放；ROS默认最多8条在途，可滚动执行1..128段。
STM32 `Wait(id, ms)` 每次从调用时计时，ms必须>0；ROS Trajectory的timeout是整个动作组的秒数上限，0使用节点默认值。
STM32返回1成功、2超时/未知ID/零时限、3设备故障；用 `DFQueue_LastError` / `LastNotice`获取解释。
超时/故障尝试取消并发零；无效ID/零时限立即返回2，调用者负责决定是否取消。断线不保证停车到达。

## 5. 持续速度、状态查询与遥测

这些接口与队列共用外层DFLink帧，但不是排队任务：

| 发送A/B | payload | 含义 |
|---|---|---|
| 0x02/0x62 | vx,vy,wz，三个S32×10000 | 持续车体速度；发全零主动停车，无任务完成回包 |
| 0x04/0x80 | mode:U8, freq_code:U8 | 统一Odom订阅 |
| 0x0B/0x40 | 空 | STM32启动时查询校准/控制状态 |

mode=1连续、2单次。客户端“停止订阅”编码为单次模式，使连续推送结束；不是单独的停止确认。
freq_code为Hz/10：10→1、50→5、100→10、200→20、250→25、500→50；ROS还支持1000→100。STM32其他输入回落为10Hz。

统一订阅 Odom，车端按 DCar 型号自动提供相应数据，用户无需选择 Odom 模式。专业版（Pro）提供全量 Odom；非专业版提供普通 Odom，包含航向、车体系/固定里程计系速度、位置和时间戳。普通 Odom 的 roll/pitch、三轴加速度、三轴角速度为零占位，不代表真实 IMU 测量。ROS通过 `publish_imu` 控制IMU发布，默认false。

Odom回包A=0x6C/B=0x80、LEN=51、首字节version=4：

| payload偏移 | 内容 | 类型 / 缩放 |
|---|---|---|
| 0 | version=4 | U8 |
| 1,3,5 | roll,pitch,yaw | S16 /10000，rad |
| 7,9,11 | 车体系ax,ay,az | S16 /400，m/s² |
| 13,15,17 | 车体系wx,wy,wz | S16 /1800，rad/s |
| 19,21,23 | 车体系vx,vy,vz | S16 /5000，m/s |
| 25,27,29 | 固定里程计系vx,vy,vz | S16 /5000，m/s |
| 31,35,39 | 固定里程计系x,y,z | S32 /1000，m |
| 43,47 | 车端原始timestamp_ms、timestamp_us | U32小端 |

遥测缩放与运动发送的S32×10000不同。ROS消息时间戳使用主机ROS时间，位置处于连续odom系，不是经过定位的地图真值。
STM32 `car_time_int_s` 是历史字段名，接收代码保存原始timestamp_ms，不做秒转换。
状态回包A=0x8C/B=0x40，完整字段见第7节；收到后 `g_dcar_state.received=1`。

## 6. 无任务ID接口的边界

Arduino当前使用无ID帧；STM32也保留独立 `Cmd_Move_*` / `WaitMoveDone`，ROS可显式选择 `motion_protocol: legacy`。
这类帧不附加任务ID，回包是A=0x6F/B=运动命令、2字节process/notice；profile取0/1/2，不能填16..20。
它们不是队列的另一种单位模式，不能与活动队列混发。无ID等待的timeout=0可无限等待；队列Wait的0无效，两者不能混用。
十字标仍走无ID专用接口，不支持混入Trajectory；当前ROS用 `/motion` 单独调用。

本说明根据当前客户端编码/解析和离线测试编写，不构成车端固件实测或轨迹精度认证。

## 7. 状态回包与无ID运动字段

### 状态查询

发送 `A=0x0B, B=0x40, LEN=0`；接收 `A=0x8C, B=0x40`，当前STM32/Arduino至少需要12字节payload。
下面偏移均相对payload首字节，不是整帧首字节。

| 偏移 | 类型 | 当前客户端保存的含义 |
|---|---|---|
| 0 | U8 | IMU校准标志，1表示已校准 |
| 1 | U8 | 控制参数微调标志 |
| 2 | S16 LE | IMU偏置原始量，字段名后缀x100 |
| 4 | S16 LE | IMU参数2原始量，字段名后缀x10000 |
| 6 | S16 LE | IMU温度参数原始量，代码字段名后缀x10000 |
| 8 | S16 LE | 控制参数1原始量，字段名后缀x100 |
| 10 | S16 LE | 控制参数2原始量，字段名后缀x100 |

客户端直接保存这五个S16，未在解析时换算成物理量。除前两个标志外，不应把这些内部参数直接当作温度、距离或速度使用；物理定义需要车端说明。状态帧没有任务ID，不是运动完成确认。

### 无任务ID运动

全部发送 `A=0x02`，所有S32均为SI物理值乘10000的小端整数。

| B | payload线上顺序 | LEN |
|---|---|---:|
| 0x62 | vx:S32, vy:S32, wz:S32 | 12 |
| 0x63 | yaw:S32, omega:S32 | 8 |
| 0x64 | x:S32, y:S32, speed:S32, profile:U8 | 13 |
| 0x65 | x:S32, y:S32, yaw:S32, speed:S32, profile:U8 | 17 |
| 0x66 | radius:S32, yaw:S32, speed:S32, profile:U8 | 13 |

无ID的0x65字段顺序是 **x,y,yaw,speed**；队列带转向的0x64是 **x,y,speed,yaw**，且多出任务ID，不能只换B码。
无ID profile=0/1/2分别表示匀速、梯形、高精度闭环；队列grade=16..20，不能互换。

有界运动回包 `A=0x6F, B=原运动B码`，基本payload为 `[process:U8, notice:U8]`：

- `process=0xFF, notice=0`：正常完成。
- `notice=1`：当前注释定义为能力不支持或参数非法。
- `notice=0x0A`：遥控接管。
- `notice=0x62..0x66`：被对应运动指令打断。
- 其他非零notice不能当正常完成；进度字节只用于观察，不代替终态判定。

STM32和Arduino根据0xFF判断终止，不统一换算进度百分比；ROS无ID解析仅接受process=1..255，并用 `(process-1)/254` 换算非终态百分比。因此，仅凭现有客户端不能确定车端进度比例采用哪一个公式。

ROS还提供十字标接口：发送 `A=0x02, B=0x80/0x81`，payload为mode单字节；成功回包使用 `A=0x6F` 和同B码，19字节payload包含process、notice、mode和四个S32/10000。它属于独立运动功能，不是遥测订阅，不能混入队列轨迹；字段语义及NEXT绑定要求见 [ROS动作说明](../ros2/docs/motion.md)。

## 8. 操场例程的实际通信顺序

STM32 Example/PatchOnly的集成示例按以下顺序执行：

1. 初始化车端串口460800/8N1、日志串口115200/8N1；向车端发送零速度，等待约1秒后再发零速度。
2. 发送 Odom 10Hz连续订阅，间隔20ms后查询状态；服务接收并输出观察日志，等待运动前的3秒启动延时。Odom缺失不自动阻止后续队列握手。
3. 发送队列能力查询，要求能力值至少为6；查询下一ID，要求编号非零且process=16，表示设备16个队列槽空闲。
4. 按顺序入队四段：半径0.30m、yaw=+π、speed=-0.15m/s的倒行半圆；x=-0.60m的后退；同样倒行半圆；x=-0.60m同时yaw=+2π。直线speed=+0.15m/s，grade=18。
5. 每次提交等待入队确认或后续有效状态，然后提交下一段；四段提交完成后，依次等待各ID成功终态。不是等待第一段完成才提交第二段。
6. 四段完成立即回到能力/下一ID握手，开始下一圈；软件没有圈间等待。车端仍可在段末减速或微调，循环不等于全程速度非零。
7. 任一失败尝试发送取消队列和零速度，停止自动发新任务，不自动改用无ID运动重跑。

ROS默认使用同样的队列编码和四段参数；Arduino使用无ID逐段发送、逐段等待完成的方式，通信时序不同。队列回包与 Odom 遥测分别处理。

所有平台只订阅、解析和保存 Odom。ROS的 `/odom`、IMU和TF只使用新鲜 Odom，断更超过1秒后不发布旧值，有效新帧到达后恢复。

## 9. 串口抓包示例

下列均为完整十六进制帧，地址为车端0x01、客户端0x97。空格仅便于阅读。

| 用途 | 完整帧 |
|---|---|
| 发送：查询队列能力 | `DF 01 97 02 85 01 00 FD FC 02` |
| 接收示例：能力值6 | `DF 97 01 6F 85 04 10 21 06 00 FD A3 03` |
| 发送：查询下一ID | `DF 01 97 02 85 01 07 FD 03 03` |
| 接收示例：16槽空闲、下一ID7 | `DF 97 01 6F 85 04 10 28 07 00 FD AB 03` |
| 发送：Odom连续10Hz | `DF 01 97 04 80 02 01 01 FD FC 02` |
| 发送：状态查询 | `DF 01 97 0B 40 00 FD BF 02` |
| 接收示例：ID7入队确认 | `DF 97 01 6F 85 04 00 10 07 00 FD 83 03` |
| 接收示例：ID7正常完成 | `DF 97 01 6F 85 04 FF 00 07 00 FD 72 04` |

接收示例是按客户端格式构造的报文，供核对字段和校验，不代表一次真实串口抓包。
例如最后一帧的payload为 `FF 00 07 00`：完成、正常、任务ID7。它与Odom收到多少帧无关。

## 10. 实现范围与确认边界

| 内容 | 目前可以确认的范围 |
|---|---|
| 外层帧、命令号、字段顺序和缩放 | 可从STM32、Arduino、ROS编码和解析代码直接确认 |
| 队列能力、任务ID、ACK和DONE | STM32和ROS已实现，Arduino未实现队列 |
| 遥测长度检查 | STM32/Arduino接受Odom长度至少51且格式号4；ROS要求恰好51字节且格式号4 |
| 接收地址与帧校验 | STM32在流解析中检查地址；ROS通用Parser只检帧尾与校验，地址由上层消费逻辑过滤 |
| 圆弧负速度 | STM32队列、ROS队列、Arduino无ID接口允许；STM32无IDCmd_Move_Arc和ROS无ID编码器要求正速度 |
| 车端时间字段 | 客户端接收两个U32原始数；注释称timestamp_ms/us，两个计数的精确关系、回绕和同步规则需车端确认 |
| 加速度档位、微调容差、最大队列能力 | 客户端只落实档位号与通知码，不包含车端控制器实现或完整限值表 |
| 丢包重试与幂等性 | 队列客户端以原ID、原字节重试；车端是否去重、结果保存多久，需要车端实现配合 |
| 固件更新范围 | 本仓库只有客户端，不能据此断言所有车端型号已升级或所有固件均支持上述功能 |
